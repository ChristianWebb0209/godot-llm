# Tool-Calling Dataset Generation Task (task.md)

## 🎯 Objective

Generate a **high-quality JSONL dataset** for fine-tuning a model to perform **accurate, reliable tool-calling** in a Godot development environment.

This dataset will be generated by:

* Making **hundreds of OpenAI API calls**
* Each call producing **dozens to hundreds of examples**
* Using **structured seeds per batch** to maximize diversity

So, I want you to build scripts that will repeatedly batch and call the OpenAI API to generate these examples, and put them into a single file. We must strictly follow every specification in this document, otherwise we will get a crazy amount of inaccuracies after training.

⚠️ This process:

* **Will take time**
* **Will cost credits**
* **Is intentional and necessary for quality**

We are optimizing for:

> **maximum signal, consistency, and behavioral reliability**

---

# 📦 Output Format

Each line must be a valid JSON object:

```json
{
  "messages": [
    {"role": "system", "content": "..."},
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."}
  ]
}
```

---

# 🔥 CRITICAL FORMATTING RULES (NON-NEGOTIABLE)

## ✅ Tool Call Format (STRICT)

ALL tool calls MUST be expressed as:

```xml
<assistant>
<tool_call>
{"name": "tool_name", "arguments": {...}}
</tool_call>
</assistant>
```

---

## ❌ NEVER DO THIS

* Do NOT use `"tool_calls"` field
* Do NOT mix natural language + tool call
* Do NOT include explanations alongside tool calls
* Do NOT output malformed JSON
* Do NOT use string or list arguments

---

## ✅ Arguments MUST be a dictionary

```json
{"arguments": {"query": "player movement"}}
```

---

## ✅ Multiple Tool Calls

Each tool call must be its own block:

```xml
<assistant>
<tool_call>
{"name": "create_node", "arguments": {...}}
</tool_call>
<tool_call>
{"name": "create_node", "arguments": {...}}
</tool_call>
</assistant>
```

---

# 🧠 DATASET COMPOSITION

Target total: **5000–7000 examples**

## 🔧 1. Tool-Use Examples (~60%)

* Clear, unambiguous intent
* Short prompts
* Minimal context
* Strong tool-to-intent mapping

---

## 🚫 2. Negative Examples (~20%)

* NO tool calls
* Pure explanations / answers

---

## ⚡ 3. Sharp Synthetic Triggers (~15–20%)

* Extremely short
* Highly consistent patterns
* High training signal

---

## 🔁 4. Correction / Retry (~5–10%)

* Tool fails → improved retry
* Teaches robustness

---

# 🧩 TOOL DEFINITIONS

All tools, their names, and argument schemas are defined in:

> **`tools.json`**

## ❗ Requirements:

* ONLY use tools defined in `tools.json`
* EXACTLY match:

  * tool names
  * argument keys
  * argument structure
* DO NOT invent or modify tools

---

# 🌱 SEED-DRIVEN GENERATION (CORE SYSTEM)

Each API call is a **batch**, controlled by a structured seed.

## ✅ Seed Structure

```python
{
  "node_types": [...],
  "extends_classes": [...],
  "scene_paths": [...],
  "script_paths": [...],
  "tools_to_prioritize": [...],
  "style": "concise | casual | technical | beginner | directive"
}
```

---

## ✅ Seed Purpose

Each batch must:

* Use the provided values to vary examples
* Prioritize listed tools
* Avoid repeating identical tool + argument combinations
* Follow the specified **style tone**

---

## 🔧 Instruction Injection

Each batch includes:

> “FOCUS for this batch (use these to vary examples; do not duplicate the same tool+key_args in this batch): ...”

---

## 💥 Key Rule

Within a batch:

> **DO NOT repeat the same tool call with identical arguments**

Across batches:

* Reuse is allowed
* Variation is expected

---

# 🧠 STYLE VARIATION

Each batch includes a style:

| Style     | Description             |
| --------- | ----------------------- |
| concise   | short, direct           |
| casual    | natural, conversational |
| technical | precise, formal         |
| beginner  | simple wording          |
| directive | command-style           |

---

## ❗ Style Rules

* Style affects ONLY phrasing
* NEVER affects:

  * format
  * schema
  * tool structure

---

# ✍️ PROMPT DESIGN RULES

## ✅ GOOD

* "Find scripts that extend Node2D"
* "Create a player movement script"
* "Search docs for signals"

---

## ❌ BAD

* Overly verbose prompts
* Unrealistic phrasing
* Ambiguous intent (unless intentional borderline case)

---

# ⚖️ TOOL USAGE DECISION BOUNDARY

Include all three:

## ✔ Tool Required

* "List all scenes"
* "Search project for X"

## ✔ No Tool

* "What is Node2D?"
* "Explain signals"

## ✔ Borderline

* "How do I check errors?" → NO tool
* "Check errors in my project" → tool

---

# 🧼 CONSISTENCY RULES

* Identical tool names
* No schema drift
* No formatting variation
